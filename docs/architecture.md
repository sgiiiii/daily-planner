# Архитектура

Приложение — один процесс Python, который отдаёт статический интерфейс и REST API,
хранит данные в SQLite и держит фоновый поток планировщика.

```
браузер ──HTTP──> server/app.py   (локально, http.server)  ─┐
                server/wsgi.py  (продакшен, gunicorn)     ─┴──> server/api.py
                                                                  │
                              server/auth.py (пароли, сессии) <───┤
                              server/planner.py (правила)     <───┤
                              server/db.py ──> SQLite | PostgreSQL
                              server/static.py ──> web/ (HTML, CSS, ES-модули)
```

## Слои

| Модуль | Ответственность | Чего не делает |
| --- | --- | --- |
| `server/app.py` | HTTP, cookie, статика, запуск, планировщик | не знает правил задач |
| `server/api.py` | маршруты, валидация входа, права, JSON | не пишет SQL напрямую (кроме мелочей) |
| `server/planner.py` | задачи, события, перенос, статистика, итоги | не знает про HTTP |
| `server/auth.py` | хэширование паролей, сессии | не знает про задачи |
| `server/db.py` | схема, подключение, транзакции | — |

Ошибки бизнес-логики поднимаются как `ApiError(status, code, message, fields)`;
`app.py` превращает их в `{"error": {...}}` с тем же HTTP-кодом. Клиент показывает
`message` и подсвечивает поля из `fields`.

## Схема базы

```
users(id, login UNIQUE, name, pwd_salt, pwd_hash, theme, rollover_time,
      summary_enabled, created_at, last_rollover)

sessions(token PK, user_id → users, created_at, expires_at)

tasks(id, user_id → users, title, note, sphere, priority, due_date, due_time,
      done, done_at, carried, carried_from, created_at, updated_at,
      deleted_at, cancelled_at)

events(id, user_id → users, title, date, start_time, end_time, kind,
       created_at, deleted_at)

day_reviews(user_id, date, confirmed_at, PRIMARY KEY(user_id, date))
```

Особенности:

* включены `foreign_keys=ON` и `journal_mode=WAL`, поэтому веб-потоки и планировщик
  не мешают друг другу;
* удаление задачи — мягкое (`deleted_at`), это даёт кнопку «Вернуть»;
* `carried`/`carried_from` хранят историю переноса, а не отдельную таблицу;
* `day_reviews` фиксирует, что пользователь подвёл итог конкретного дня.

## Жизненный цикл задачи

| Состояние | Как достигается |
| --- | --- |
| `open` | задача создана на сегодня или будущую дату |
| `carried` | задача перенесена, `carried > 0` |
| `overdue` | срок раньше сегодняшнего дня, задача не выполнена |
| `done` | отмечена выполненной, `done_at` заполнен |
| `deleted` | мягкое удаление, доступно восстановление |

Статус не хранится отдельным полем: он вычисляется в `planner.task_json()` из
`done`, `due_date`, `carried`, `deleted_at`. Так невозможно получить
рассогласованные данные.

## Перенос невыполненных задач

Правило: задача со сроком раньше сегодняшнего и `done = 0` получает
`due_date = сегодня`, `carried += 1`, `carried_from = прежний срок`.

Запускается двумя путями:

1. **Фоновый планировщик** — поток в `app.py`, раз в 30 секунд смотрит пользователей
   и вызывает `planner.rollover_if_due()`. Перенос выполняется один раз в день,
   после времени из `users.rollover_time`; факт выполнения пишется в `last_rollover`.
2. **Ленивая проверка** — при любом авторизованном запросе. Если сервер был выключен
   в 04:00, перенос произойдёт при первом открытии приложения.

Такая схема устойчива к перезапускам, не требует cron и не переносит задачи
дважды. Ручной запуск доступен из профиля (`POST /api/rollover`).

## Две базы и два транспорта

Локально и на хостинге работает один и тот же код, отличаются только драйвер
базы и транспорт HTTP.

**База.** `server/db.py` выбирает SQLite или PostgreSQL по `DATABASE_URL`.
Остальной код пишет SQL с плейсхолдерами `?` и получает `row["колонка"]`:

* адаптер подменяет `?` на `%s` для psycopg;
* `insert_returning_id()` использует `RETURNING id` в PostgreSQL и `lastrowid`
  в SQLite;
* схема описана двумя вариантами (`BIGSERIAL` против `AUTOINCREMENT`);
* поиск использует `ILIKE` в PostgreSQL и `LIKE` в SQLite;
* `PLANNER_DB_RESET=1` удаляет таблицы (нужно тестам, на рабочей базе нельзя).

**Транспорт.** `server/app.py` — локальный `ThreadingHTTPServer`,
`server/wsgi.py` — WSGI-приложение для gunicorn и хостингов. Оба используют
общие модули: `api.dispatch`, `static.resolve`, `scheduler`.
WSGI-вариант при первом запросе применяет схему, сеет демо-данные (если
`PLANNER_SEED_DEMO=1`) и запускает планировщик.

**Несколько процессов.** Перенос в `planner.rollover_if_due` сначала атомарно
«занимает» день обновлением `users.last_rollover` и продолжает только при
`rowcount = 1`. Поэтому несколько worker-процессов gunicorn не переносят задачи
дважды.

**Настройки окружения**

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `DATABASE_URL` | — | включает PostgreSQL |
| `PLANNER_SEED_DEMO` | `1` | демо-аккаунт `demo/demo1234` |
| `PLANNER_SCHEDULER` | `1` | фоновый перенос задач |
| `PLANNER_COOKIE_SECURE` | `0` | флаг Secure у cookie (HTTPS) |
| `PLANNER_DB` | `data/planner.db` | файл SQLite |
| `PLANNER_DB_RESET` | `0` | удалить таблицы при старте (тесты) |

`GET /api/config` отдаёт публичные флаги интерфейсу — например, `demoEnabled`,
чтобы не показывать демо-доступ на публичном сайте.
## Сводка и итоги

* `GET /api/summary` — статистика дня, до пяти открытых задач в порядке
  «приоритет → время», перенесённые, просроченные, встречи, ближайшее событие,
  количество задач на завтра и признак «итог уже подведён».
* `GET /api/review` — выполненные и открытые задачи дня плюс все просроченные.
* `POST /api/review/confirm` — фиксирует итог в `day_reviews` и возвращает числа
  для финального экрана.
* `POST /api/tasks/{id}/carry` — перенос одной задачи; отмена делается обычным
  `PATCH` с возвратом даты и `carried = 0`.

## Интерфейс

* `web/js/app.js` — каркас, история (`pushState`), темы, горячие клавиши, общие
  действия (`openTaskForm`, `openTaskDetail`, `refresh`).
* Каждый экран — модуль с методом `mount(root, app)`. Внутри своего `draw()` он
  перерисовывает содержимое и переиспользует делегирование событий, поэтому нет
  утечек обработчиков при обновлении списка.
* Тема хранится в аккаунте (`users.theme`) и дублируется в `localStorage`, чтобы
  не мигать при загрузке. `data-theme` на `<html>` переключает семантические
  токены; системная тема слушается через `prefers-color-scheme`.
* Диалоги — нативные `<dialog>`: фокус-ловушка, `Esc` и подложка работают без
  собственного кода. Содержимое меняется на месте, чтобы не ловить гонку с
  событием `close`.
* Тосты складываются максимум по три и очищаются при смене экрана; у действий
  есть отмена.

## Обработка ошибок

* клиент бросает `ApiError` с `status`, `code`, `fields`;
* 401 в любом запросе, кроме входа, разлогинивает и показывает экран входа;
* формы показывают ошибку под конкретным полем;
* загрузка списка показывает скелетон, ошибка — блок с кнопкой «Повторить»;
* на сервере необработанные исключения логируются и превращаются в 500 без
  утечки трассировки клиенту.
